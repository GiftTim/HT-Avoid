b. 요구한 기능
================================================================

  기존에 만들어 둔 "클릭 시 공격 판정"(PlayerAttack.cs)이 판정만 있고
  눈에 보이는 결과가 없어 확인이 어려움 — 아래 4가지를 추가해 눈으로
  확인 가능한 상태로 보강한다 (26.09.15 요청):

  1. 확인용 테스트 대상 Enemy1/Enemy2/Enemy3 를 만든다. 공격 판정에
     맞으면 오브젝트가 사라지고, Console에 "공격당했다"는 로그를 남긴다
  2. 마우스 클릭 시 기본 공격이 나가는 것과 동시에 Player 자식 오브젝트인
     AttackEffect가 나타났다가 약 1초 뒤 사라진다. 이 "몇 초 뒤 사라지는지"
     값은 실험해볼 수 있도록 인스펙터에서 조절 가능해야 한다
  3. AttackEffect는 Player의 중심에서 시작해서, 공격 범위만큼 Scale의
     X축이 늘어난 형태로 표시된다 (즉 판정 범위를 눈으로 보여주는 막대/
     빔 형태)
  4. AttackEffect의 방향은 "클릭한 지점 방향 ↔ Player 중심" 을 잇는
     직선 방향 (기존 PlayerAttack의 조준 방향 계산과 동일한 벡터)

  보스 HP/연출/실제 아트 이펙트는 이번 범위 아님 (h절 참고) — 지금은
  판정이 실제로 맞는지/범위가 어느 정도인지 눈으로 확인하기 위한
  플레이스홀더 단계.

c. 현재 상황 및 코드
================================================================

  [ PlayerAttack.cs (Assets/Scripts/Avoid/Core/) — 이미 작성됨 ]
  - [RequireComponent(typeof(PlayerInput))]. AvoidInput.inputactions의
    "Attack" 액션(<Mouse>/leftButton)을 구독
  - OnAttackStarted(클릭 시) :
    1. 쿨다운(attackCooldown, 기본 0.4초) 체크
    2. TryGetAimWorldPoint() 로 마우스 스크린 좌표 → Player와 같은
       z 평면(z=0) 위 월드 좌표(aimPoint) 변환 (Camera.ScreenPointToRay
       + Plane.Raycast. Camera-Main이 Perspective라 이 변환이 필요함)
    3. direction = (aimPoint - Player위치).normalized 계산
    4. hitCenter = Player위치 + direction * attackDistance(기본 1.2)
    5. Physics2D.OverlapCircleAll(hitCenter, attackRadius(기본 0.6),
       enemyLayer) 로 판정 → 맞은 대상의 IDamageable.TakeDamage(damage)
       (damage 기본 10) 호출
  - 지금은 여기서 끝 — 시각적 이펙트도 없고, TakeDamage를 실제로 구현한
    대상(Enemy)도 아직 없어서 판정이 맞았는지 콘솔/화면 어디에도 표시가
    안 됨 (이번 ChangePlan의 동기)

  [ IDamageable.cs — 이미 작성됨 ]
  - void TakeDamage(int amount) 하나만 있는 인터페이스. 구현체는 아직
    프로젝트에 하나도 없음 (Enemy1/2/3가 최초 구현체가 됨)

  [ 레이어 설정 — 이미 되어 있음 ]
  - ProjectSettings/TagManager.asset 9번 레이어가 "Enemy"로 지정되어
    있고, PlayerAttack의 enemyLayer 필드도 씬에서 이미 Enemy(512)로
    연결되어 있음 → Enemy1/2/3를 이 레이어에 놓기만 하면 별도 코드
    수정 없이 바로 판정 대상이 됨

  [ Player 오브젝트 (Assets/Scenes/Avoid.unity) ]
  - Rigidbody2D + BoxCollider2D + SpriteRenderer + PlayerInput +
    MovementRigidbody2D + AvoidPlayerController + PlayerAttack 부착
  - Transform : localPosition (0, -3.75, 0), localScale (0.5, 0.5, 0.5)
    → AttackEffect를 자식으로 두면 부모의 0.5배 스케일이 곱해지므로,
      길이를 attackDistance와 맞추려면 코드에서 이 배율을 보정해야 함
      (h절 참고)

  [ AttackEffect ]
  - 아직 없음. 신규 생성 필요 (d절)

  [ Enemy1/2/3 ]
  - 아직 없음. 신규 생성 필요 (d절). 참고 아트/스프라이트 없음 →
    플레이스홀더로 진행

d. 요구한 기능을 만들기 위해서 어떤 식으로 생성하거나 변경해야 하는지
================================================================

  1) 신규 스크립트 : Assets/Scripts/Avoid/Core/Enemy.cs
     - MonoBehaviour, IDamageable 구현
     - TakeDamage(int amount) :
       1. Debug.Log($"{name} 공격당함 (피해량: {amount})") 로 콘솔 표시
       2. Destroy(gameObject) 로 즉시 제거("맞으면 사라진다" 요구사항)
     - Collider2D(트리거 권장, 예: CircleCollider2D)만 있으면 되고
       Rigidbody2D는 필요 없음(공격 판정은 OverlapCircleAll이 위치
       기준으로 검사하므로 물리 시뮬레이션 불필요)

  2) PlayerAttack.cs 확장 (기존 파일 수정)
     - 신규 인스펙터 필드 추가 :
       · [SerializeField] private Transform attackEffectTransform
         (Player 자식 AttackEffect 연결용)
       · [SerializeField] private SpriteRenderer attackEffectRenderer
         (표시/숨김 제어용)
       · [SerializeField] private float effectDuration = 1f
         (요구사항 2 — 인스펙터에서 조절 가능한 "몇 초 뒤 사라지는지" 값)
     - OnAttackStarted 안, 기존 판정 로직(hitCenter 계산) 직후에
       ShowAttackEffect(direction) 호출 추가
     - ShowAttackEffect(Vector2 direction) 신규 메서드 :
       1. float angle = Mathf.Atan2(direction.y, direction.x) * Mathf.Rad2Deg
          → attackEffectTransform.localRotation = Quaternion.Euler(0, 0, angle)
       2. float parentScaleX = transform.lossyScale.x (Player의 실제
          월드 스케일, 기본 0.5) → 길이 보정
       3. attackEffectTransform.localPosition =
          Vector3(direction * (attackDistance * 0.5f) / parentScaleX, 0)
          (로컬 좌표라 부모 스케일이 또 곱해지므로 미리 나눠서 상쇄)
       4. attackEffectTransform.localScale =
          new Vector3(attackDistance / parentScaleX, 기존 Y/Z 유지, ...)
       5. attackEffectRenderer.enabled = true (또는 gameObject.SetActive(true))
       6. 기존에 실행 중이던 숨김 코루틴이 있으면 StopCoroutine으로 취소
          하고 새로 StartCoroutine(HideEffectAfterDelay()) 시작
          (연타 시 이전 타이머 때문에 중간에 꺼지는 것 방지)
     - HideEffectAfterDelay() 코루틴 : yield return new
       WaitForSeconds(effectDuration) 후 attackEffectRenderer.enabled = false

     ※ "Player 중심에서 시작해서 범위만큼 늘어난다"를 스프라이트 피벗
       수정 없이 구현하는 방법 : 스프라이트의 기본 피벗(중앙)을 그대로
       두고, 오브젝트의 중심 자체를 "Player중심~사거리끝 구간의 중점"에
       놓은 뒤 그만큼 늘린다. 즉 로컬 위치 = 방향 × (사거리 / 2),
       스케일 X = 사거리로 설정하면, 회전된 사각형이 정확히 Player
       중심에서 시작해서 사거리 끝까지 뻗는 모양이 된다 (e절 참고)

  3) 신규 오브젝트 : AttackEffect (Player의 자식, 씬에 직접 배치)
     - SpriteRenderer 부착. Source Sprite는 Unity 기본 내장 사각형
       스프라이트 사용 (Editor에서 GameObject > 2D Object > Sprites >
       Square 로 생성 시 자동 할당되는 스프라이트 — 별도 아트 리소스
       불필요, e절 참고)
     - 시작 상태는 비활성(SpriteRenderer.enabled = false 또는
       GameObject 자체를 Inactive)
     - Collider 불필요(판정은 PlayerAttack의 OverlapCircleAll이 이미
       따로 하고 있으므로, 이 오브젝트는 순수 시각 표시 전용)

  4) 신규 오브젝트 : Enemy1 / Enemy2 / Enemy3 (씬에 직접 배치)
     - 각각 Enemy.cs + Collider2D(Trigger) 부착
     - Layer를 "Enemy"(9번)로 지정 — 이미 PlayerAttack의 enemyLayer가
       이 레이어를 보고 있으므로 이것만 맞추면 됨
     - SpriteRenderer로 서로 구분되는 임시 색(예: 빨강/초록/파랑) 또는
       Unity 기본 Square 스프라이트 + 다른 Color 값으로 구분
     - Player 공격 범위(대략 attackDistance ± attackRadius) 안에 들어
       오도록 Player 근처에 나란히 배치 (테스트 편의성)

e. 다른 방법들 중에서 왜 d의 방식으로 만든 것인지
================================================================

  [ 피격 시 사라지는 방식 ]
  - 대안 1 : SetActive(false)로 비활성화만
    · 장점 : 나중에 재사용(리스폰) 가능
    · 단점 : 지금은 "확인용 1회성 테스트 오브젝트"일 뿐이라 재사용할
      이유가 없고, 요구사항도 "사라진다"로 명시함 → 기각
  - 대안 2 (채택) : Destroy(gameObject)
    · 요구사항 그대로("사라진다") 구현, 코드도 제일 단순
    → 테스트 목적에 맞춰 채택. 실제 보스/적 시스템(HP/사망 연출 등)은
      후속 ChangePlan에서 별도로 설계 예정 (h절 참고)

  [ 공격 이펙트의 "Player 중심에서 시작해서 늘어나는" 모양 구현 방식 ]
  - 대안 1 : 스프라이트 자체의 피벗(Pivot)을 왼쪽 끝으로 옮겨서, 위치는
    항상 Player 중심 고정하고 Scale.x만 늘리기
    · 장점 : 코드에서 위치 계산을 안 해도 됨(피벗이 알아서 왼쪽에 고정)
    · 단점 : 참고 아트가 없어 플레이스홀더 스프라이트를 쓰는데, Unity
      기본 내장 스프라이트는 Sprite Editor로 피벗을 수정할 수 있는
      "내 프로젝트 소속 텍스처"가 아니라 임포트 설정을 바꿀 수 없음.
      즉 이 방식을 쓰려면 실제 이미지 파일을 새로 만들어 임포트하고
      Pivot을 Custom(0, 0.5)로 지정하는 에디터 작업이 추가로 필요함 →
      지금 단계(플레이스홀더 확인용)에서는 과함 → 기각
  - 대안 2 (채택) : 피벗은 중앙 그대로 두고, 오브젝트 위치를
    "Player중심~사거리 끝의 중점"으로 계산해서 배치 + Scale.x만 사거리로
    설정
    · 장점 : 기본 내장 스프라이트를 그대로 쓸 수 있어 별도 아트/임포트
      작업이 전혀 필요 없음(코드만으로 완결). 회전-이동-스케일 세
      값만 계산하면 되므로 로직도 짧음
    · 단점 : 위치 계산식(중점, 부모 스케일 보정)이 한 줄 더 필요하지만
      감수 가능한 수준
    → 아트 리소스가 없는 지금 상황(참고 자료 없음)에 맞춰 채택

  [ 이펙트를 켜고 끄는 방식 ]
  - 대안 1 : Instantiate/Destroy로 매 공격마다 새로 생성/파괴
    · 장점 : Player에 미리 자식으로 붙여둘 필요 없음
    · 단점 : 요구사항이 "Player밑에 있는 AttackEffect"라고 명시적으로
      고정된 자식 오브젝트를 전제하고 있고, 매번 생성/파괴하면 GC
      비용도 불필요하게 발생 → 기각
  - 대안 2 (채택) : 씬에 미리 배치된 고정 자식 오브젝트를 SpriteRenderer.
    enabled로 껐다 켰다
    · 요구사항과 정확히 일치, 성능도 더 좋음
    → 채택

  [ "몇 초 뒤 사라지는지" 타이머 구현 방식 ]
  - 대안 1 : Invoke("HideEffect", effectDuration)
    · 장점 : 코드가 짧음
    · 단점 : 연타로 공격 시 이전 Invoke가 취소되지 않고 누적되어, 늦게
      예약된 Invoke가 중간에 이펙트를 꺼버리는 꼬임이 생길 수 있음
      (CancelInvoke로 매번 정리해야 하는데 코루틴보다 가독성이 떨어짐)
      → 기각
  - 대안 2 (채택) : 코루틴(StartCoroutine/StopCoroutine)
    · 이전 코루틴을 명시적으로 참조 변수에 들고 있다가 새 공격 시
      StopCoroutine으로 확실히 취소하고 다시 시작 → 연타해도 항상
      "마지막 공격 시점 + effectDuration"에 정확히 사라짐
    → 채택

  5. (에디터) Enemy1/Enemy2/Enemy3 오브젝트를 Player 공격 범위 안에

     부착, 서로 구분되는 임시 색 지정

     Player 중심에서 사거리만큼 뻗어 나왔다가 인스펙터에 지정한
     effectDuration 뒤 사라지는지, Enemy가 사라지며 콘솔에 로그가
     찍히는지 확인

h. 주의할 점
================================================================

  ■ Player의 localScale이 (0.5, 0.5, 0.5)라서, AttackEffect가 그
    자식이면 로컬 Scale/Position에 부모 스케일이 곱해서 적용됨 →
    d절 2)처럼 transform.lossyScale.x로 나눠서 미리 상쇄하지 않으면
    이펙트 길이가 실제 공격 범위(attackDistance)의 절반으로 보임
    (Player 스케일이 나중에 바뀌면 이 보정값도 같이 흔들리므로,
    이후 세션에서 Player 스케일을 조정하게 되면 이 부분을 다시 확인
    해야 함)

  ■ 이번 AttackEffect/Enemy는 전부 "판정 범위를 눈으로 확인하기 위한
    플레이스홀더"이며, 실제 슬래시 아트/파티클, 보스 HP/피격 연출,
    Enemy의 사망 이펙트/사운드 등은 이번 범위 밖 (참고 자료도 아직
    없음 — 후속 ChangePlan에서 실제 아트가 준비되면 다시 다룸)

  ■ Enemy1/2/3는 이번엔 "맞으면 즉시 Destroy"로 충분하지만, 실제
    보스/적 시스템에서는 HP 개념이 필요할 것으로 보임(로드맵 상
    "보스 HP 0 → 클리어" 조건과 연결). IDamageable 인터페이스 자체는
    그대로 재사용 가능하지만, TakeDamage 구현부(지금은 즉시 Destroy)는
    보스 설계 단계(로드맵 5단계)에서 HP 차감 방식으로 교체될 예정 —
    지금 Enemy.cs를 보스 스크립트의 기반으로 재사용하려 하지 말고
    별개의 테스트용 클래스로 취급할 것

  ■ AttackEffect의 Collider는 만들지 않음 — 판정은 여전히 PlayerAttack의
    OverlapCircleAll이 담당하고, AttackEffect는 순수 시각 표시용이라
    실제 판정 범위(원형)와 이펙트 모양(막대형 사각형)이 시각적으로
    정확히 일치하지는 않음(사각형은 범위를 "대략적으로" 보여주는
    용도). 정밀하게 원형 판정 모양까지 맞추는 것은 이번 요구사항에
    없어 범위 밖으로 둠
