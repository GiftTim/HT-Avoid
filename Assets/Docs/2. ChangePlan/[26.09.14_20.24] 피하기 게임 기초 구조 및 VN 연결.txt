b. 요구한 기능
================================================================

  로드맵 2단계("피하기 게임 캐릭터 인터페이스 및 VN 연결")의 최초
  뼈대를 만든다. 범위는 아래 3가지로 확정(26.09.14 설계 대화, 그 중
  1./3.은 최초 초안 작성 후 같은 날 사용자가 다시 수정 지시함 — h절
  "변경 이력" 참고):

  1. 피하기 게임의 화면 구성 (26.09.14 최종) : 사이드스크롤 플랫폼
     (메이플스토리 형식) — 좌우 이동 + 점프(중력 있음), 마우스 조준
     공격, 좌우 박스 벽에 막히는 경계
  2. VN ↔ 피하기 게임의 씬 레벨 연결 방식 : 애디티브 씬 로딩
  3. "캐릭터 인터페이스" (26.09.14 최종) : VN 캐릭터(Lia/Mari/Mina/
     Rachel/Raelin 등)는 피하기 게임에서 "보스"로 등장한다. 주인공
     (플레이어)은 VN 로스터와 무관한 별도의 고정 캐릭터 1인이며,
     주인공이 VN 캐릭터(보스)의 공격을 피하고 공격하는 형식

  보스 HP/패턴/탄막 스포너/히트박스 판정 방식/카드(스킬) 연동은 각각
  3~5단계 및 후속 ChangePlan에서 다룸 (h절 참고, 이번 범위 아님)

     - 좌우 박스 벽은 시각적 가이드로만 배치, 실제 좌우 이동 제한은
       코드에서 처리 (Mathf.Clamp 기반, 바닥/점프는 물리 충돌 사용)

  2) 신규/변경 폴더 : Assets/Scripts/Avoid/
     - Avoid/Data/AvoidCharacterProfile.cs (보스용, 재정의)
       · ScriptableObject. characterKey(string, Character.name/alias와
         매칭), idleAnimation/hitAnimation/attackAnimation(우선은
         AnimationClip 참조 필드로 최소 정의, 실제 애니메이션 시스템은

       · ScriptableObject. VN 로스터와 무관한 고정 캐릭터 1인용이라
         characterKey로 여러 개를 관리하지 않고 단일 애셋을 만들어
         인스펙터에 직접 연결. idleAnimation/moveAnimation/
         jumpAnimation/hitAnimation/attackAnimation + hitboxRadius

       (26.09.15 수정 — 애초 계획은 한 클래스였으나 실제로는 입력과

         입력을 직접 읽지 않고 MoveTo(float x)/JumpTo()/IsLongJump 같은
         공개 API만 제공. FixedUpdate에서 자신의 Collider2D.bounds로

         AvoidInput.inputactions(Player 맵 — Move: A/D 1D Axis,
         Jump: Space)에서 액션을 읽어 MovementRigidbody2D의 API로
         전달. Move는 FixedUpdate에서 ReadValue<float>()로 매 프레임
         폴링, Jump는 started/canceled 이벤트로 IsLongJump 토글
         (VN 쪽 PlayerInputManager.cs와 같은 Input Action 패턴 — e절
         "입력 처리 방식" 참고)
       · 좌우 박스 벽 경계(AvoidSceneController.BoxHalfExtents.x Clamp)와
         마우스 조준/Initialize(PlayerCharacterProfile)는 아직 미반영

     - Avoid/Core/AvoidBossController.cs (신규)
       · ApplyProfile(AvoidCharacterProfile) 메서드만 가진 최소
         컴포넌트. 실제 탄막/패턴/HP는 5단계에서 구현
     - Avoid/Core/AvoidSceneController.cs (재작성)
       · player/boss/playerProfile 참조를 인스펙터에서 받음
       · Start()에서 player.Initialize(playerProfile) 로 고정
         주인공 프로필을 항상 적용
       · Setup(string characterKey) : 이번 전투에서 보스로 등장할

         불러와 boss.ApplyProfile(profile) 호출
       · 씬이 로드된 직후 커맨드 쪽에서 이 컴포넌트를 찾아 Setup을
         호출하는 구조 (연결 방식은 3) 참고)

  3) 파일 : Assets/Scripts/VisualNovel/Core/Commands/Database/

e. 다른 방법들 중에서 왜 d의 방식으로 만든 것인지
================================================================

  [ VN↔피하기 연결 방식 ]
  - 대안 1 : 별도 씬 + SceneManager.LoadScene(단일 모드)
    · 장점 : 씬 파일이 완전히 분리됨
    · 단점 : c절에서 확인했듯 VN 싱글톤들이 DontDestroyOnLoad가 아니라
      전환 시 전부 파괴됨. 대화 진행상태/변수를 세이브→로드로 왕복
      시켜야 하는데, 세이브 데이터 구조 확장은 4단계(인벤토리)부터
      하기로 이미 결정되어 있어(26.09.13/26.09.14 로드맵) 시기상 맞지
      않음 → 기각
  - 대안 2 : 같은 씬 안에서 루트 오브젝트 SetActive 토글
    · 장점 : 싱글톤 파괴 문제 없음, 구현이 제일 단순
    · 단점 : 3~5단계(스킬/인벤토리/보스) 콘텐츠까지 전부 한 씬 파일에
      쌓여서 나중에 씬이 비대해짐 → 기각(완전히 나쁜 방법은 아니라
      추후 상황이 바뀌면 재검토 가능)
  - 대안 3 (채택) : 애디티브 씬 로딩 (LoadSceneMode.Additive)
    · VN 씬을 언로드하지 않은 채 Avoid 씬을 위에 얹으므로 싱글톤
      파괴 문제가 없고(대안 1의 단점 해결), 동시에 씬 파일 자체는
      목적별로 분리됨(대안 2의 단점 해결)
    · 단점 : 패널 토글보다 전환 코드가 조금 더 필요(로딩 대기, 씬
      탐색으로 컨트롤러 참조 확보)하지만 감수 가능한 수준
    → 사용자가 직접 이 방식으로 결정 (26.09.14)

  [ 캐릭터 게임플레이 데이터 위치 ]
  - 대안 1 : 기존 CharacterConfigData.cs 에 필드 추가
    · 장점 : 새 클래스 없이 빠르게 처리 가능
    · 단점 : VN 표시용 데이터(이름색/폰트 등)와 게임플레이 스탯이 한
      파일에 섞여 관심사가 분리되지 않음 → 기각
  - 대안 2 (채택) : AvoidCharacterProfile 이라는 별도 ScriptableObject로
    분리, characterKey로 기존 Character.name/alias와 연결
    · VN 표시 계층과 피하기 게임플레이 계층이 완전히 분리되어, 나중에
      3단계 카드/4단계 인벤토리 데이터도 같은 Avoid/Data/ 폴더 규칙으로
      자연스럽게 확장 가능
    → 사용자가 직접 이 방식으로 결정 (26.09.14)

  [ 이동 방식 (26.09.14, 화면 구성을 사이드스크롤로 바꾸면서 추가 결정) ]
  - 대안 1 : 좌우+상하 자유 이동, 중력/발판 없음 (최초 탑다운 이동
    로직을 시점만 바꿔서 재사용)
    · 장점 : 구현이 제일 단순, 이미 짜둔 코드를 거의 그대로 씀
    · 단점 : "메이플스토리 형식"이라는 요구와 맞지 않음(진짜 플랫폼
      느낌이 안 남) → 기각
  - 대안 2 (채택) : 중력/점프 있는 진짜 플랫폼 (Rigidbody2D +
    groundCheck 기반)
    · 장점 : 메이플스토리 보스전 느낌을 실제로 구현. 나중에 발판/맵
      디자인을 확장할 여지가 생김
    · 단점 : 발판 Collider2D 배치 등 씬 구성이 좀 더 필요(에디터에서
      직접 작업) → 감수 가능한 수준
    → 사용자가 직접 이 방식으로 결정 (26.09.14)

  [ 입력 처리 방식 (26.09.15 추가 결정) ]
  - 대안 1 : 구식 Input Manager(Input.GetKey/GetAxis)로 직접 읽기
    · 장점 : 코드가 제일 짧음
    · 단점 : VN 쪽(PlayerInputManager.cs)이 이미 PlayerInput + Input
      Action Asset 구조로 되어 있어서, 여기만 구식 방식을 쓰면 입력

h. 주의할 점

  ■ 이번 ChangePlan은 "뼈대"까지만 범위로 함. 아래는 명시적으로
    이번 범위 밖이며 후속 ChangePlan에서 별도로 다룸 :
    - 실제 탄막/보스 스포너, 보스 HP/패턴 (5단계)
    - 히트박스/충돌 판정 방식(Trigger Collider vs 거리 계산) 확정
    - 박스의 정확한 크기/해상도 (지금은 임의값으로 배치 후 튜닝)
    - 플레이어 공격(마우스 조준 발사체) 의 실제 발동/쿨타임 (3단계
      스킬(카드) 시스템과 함께 설계 예정)
    - 피하기 결과(클리어/실패, 목숨 등)를 VN/RPG 쪽에 전달하는 방식
      (로드맵 f절에 "정확한 연동 방식은 미정"으로 이미 명시되어 있음)
    - endAvoid 명령은 지금은 개발자가 직접 대본에 적어 테스트하는
      임시 수단이며, 실제로는 목숨 소진/보스 처치 조건에서 코드가
      자동으로 호출해야 함 (5단계에서 교체 예정)

    처리해야 하는 항목이라 f절 7-b 단계에 구체적으로 포함시켜 둠
