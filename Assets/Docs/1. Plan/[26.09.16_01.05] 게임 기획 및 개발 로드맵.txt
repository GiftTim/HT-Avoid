d. 참고 모티브
================================================================

  [ 헬테이커 (Helltaker) ]
  - 짧은 박스 밀기 퍼즐 + 데모니스 캐릭터들과의 VN식 상호작용/호감도
  - 챕터마다 "퍼즐 방 하나 클리어 → 캐릭터와의 짧은 대화" 반복
  - 이 프로젝트가 차용하는 것 : "VN 대화 ↔ 게임플레이 구간"이 교대로
    반복되며 진행되는 큰 틀

  [ 피하기(Avoid) ]
  - 기초 : "밈피하기"류 (좁은 화면 안에서 보스의 탄막/공격 패턴을
    실시간으로 회피하는 형태의 국내 플래시류 피하기 게임)
  - 여기에 메이플스토리처럼 "플레이어도 공격 가능"한 요소를 추가
    → 순수 회피만이 아니라, 회피 + 공격을 병행하는 보스전 액션
  - 승리조건 : 보스 HP를 0으로 만들면 클리어 (메이플스토리 보스전 방식)
  - 즉 "피하기 미니게임" = 회피(밈피하기 기반) + 공격(메이플스토리풍)이
    결합된 보스 전투 파트

  [ RPG (덱빌딩) — 정체 재정의 (26.09.13) ]
  - 당초 "별도의 턴제 카드 전투"로 구상했으나, 실제로는 그런 전투가
    따로 있는 것이 아니라 "피하기 보스전에서 실시간으로 사용할
    스킬(카드)을 수집·강화·장착하는 메타 시스템"으로 확정됨
  - 스킬(카드) = 피하기 전투 중 마우스 공격/스킬 버튼에 대응하는
    실시간 액티브 스킬 (턴제로 발동하는 카드가 아님)
  - "덱빌딩"이라는 이름은 유지하되, 실제 형태는 인벤토리에 카드를
    보관하고 캐릭터별로 장착(세팅)하는 화면에 가까움
  - 카드 종류/획득 방식/강화 규칙/장착 슬롯 수 등은 아직 미정

e. 확정된 게임 사이클 구조
================================================================

    ┌───────┐     ┌────────────┐     ┌─────────────────┐     ┌───────┐
    │  VN   │ ──▶ │ 피하기 게임 │ ──▶ │ RPG (인벤토리/   │ ──▶ │  VN   │ ─┐
    │       │     │ (실시간 액션)│     │ 스킬 장착 메타) │     │       │  │
    └───────┘     └────────────┘     └─────────────────┘     └───────┘  │
        ▲                                                                │
        └────────────────────── (다음 사이클로 반복) ──────────────────┘

    이 사이클을 여러 번 반복 → 최종적으로 "보스" 구간까지 도달해 클리어
    (사이클 진행에 따라 피하기 전투 규모도 점점 확대됨 → k절 참고)

  [ 1사이클 흐름 ]
    1. VN        : 상황 설명, 캐릭터와의 대화, 다음 구간으로의 도입부
    2. 피하기    : 실시간 액션 구간 (보스 HP를 0으로 만들면 클리어.
                   성공/실패 또는 성과가 다음 단계에 영향)
    3. RPG(인벤토리/스킬 장착): 피하기 결과를 바탕으로 스킬(카드)
                   수집/강화/장착 등 다음 전투 준비
    4. VN        : 결과 반영한 후일담/다음 사이클로의 연결
    → 반복 → 보스전 → 클리어

f. 각 파트가 담당하는 역할
================================================================

  VN         : 서사 전달, 캐릭터 관계 형성, 다음 구간의 동기 부여
               (기존 엔진 그대로 사용 — 대사/커맨드/캐릭터/그래픽/오디오)

  피하기     : 순간적인 텐션/액션 담당. 회피 + 공격을 병행해 보스 HP를
               0으로 만드는 것이 목표. 결과(클리어/실패, 점수 등)가
               다음 RPG 파트의 시작 조건(예: 자원량, 카드 드로우 수)에
               영향을 주는 것으로 설계 (정확한 연동 방식은 미정)

  RPG(인벤토리/스킬 장착): 전투가 아니라 준비 단계. 여기서 정한 스킬
               (카드) 구성이 다음 피하기 전투에서 실제로 사용할
               액티브 스킬이 됨. 여기서의 결과(장착 구성 등)가 다음
               VN 파트의 분기(엔딩/호감도/스토리 전개)에도 반영되는
               것으로 설계 (VariableStore를 통해 VN 쪽 조건문과 연결 가능)

  보스전     : 사이클의 최종 관문. 지금까지 쌓은 스킬(카드) 구성과
               피하기 숙련도를 종합적으로 시험하는 구간. 일반 사이클의
               피하기보다 훨씬 큰 규모의 풀 보스전으로 진행

g. 구현 시 필요한 신규 시스템
================================================================

  1. 피하기(Avoid) 미니게임 엔진 (= 보스 전투 파트)
     - 회피 : 플레이어 이동/충돌 판정, 보스 탄막/공격 패턴 스폰 (밈피하기 기반)
     - 공격 : 플레이어 공격 판정, 보스 체력/피격 처리 (메이플스토리풍)
     - 조작 : 키보드(이동) + 마우스(공격/스킬) 혼합 (확정, 26.09.13)
       · 카타나 제로(Katana Zero) 모티브로 구체화 (확정, 26.09.15) :
         WASD 이동 + 마우스로 공격 위치/방향 지정 + 클릭으로 공격
       · 단, 카타나 제로는 방 단위 던전 구조인 반면 이 프로젝트는
         던전 없이 곧바로 보스전으로 진입하는 구조 (확정, 26.09.15)
     - 승리조건 : 보스 HP 0 (확정)
     - 시간 제한 : 보스마다 개별 설정. 기본은 무제한 딜링이되, 일부
       보스는 특정 페이즈에서 타임어택 압박을 줌 (확정, 26.09.13)
     - 목숨/사망 처리 (확정, 26.09.13)
       · 목숨 3개
       · 사망 시 "대기방"으로 이동 후 재도전 (메이플식)
       · 재도전 시 보스 HP는 사망 직전 상태 그대로 유지 (리셋 안 됨)
       · 목숨 3개를 모두 소진하면 진짜 게임오버 → 타이틀/메인메뉴로
         이동, 마지막 자동저장 지점부터 재개 (→ h절 세이브 연동 참고)
     - 전투 규모 : 사이클이 진행될수록 점점 확대 (초반 사이클은 약식
       회피 위주, 후반으로 갈수록 풀 보스전) (확정, 26.09.13)
     - 보스 : 패턴 설계(페이즈 전환 등), 처치 시 결과값(점수/생존시간 등) 산출
     - 신규 폴더 제안 : Assets/Scripts/Avoid/

  2. 스킬(카드) 시스템 (RPG(덱빌딩)의 실체, 확정 26.09.13)
     - 카드 = 피하기 보스전 중 실시간으로 발동하는 액티브 스킬
       (턴제 카드 배틀이 아님)
     - 카드 데이터(ScriptableObject), 쿨타임/발동 조건 등
     - 신규 폴더 제안 : Assets/Scripts/Skills/ (또는 Cards/)

  3. 인벤토리 시스템 (카드 보관 + 캐릭터 장착)
     - 보유 카드 보관, 캐릭터별 장착 슬롯 관리 UI/데이터
     - 신규 폴더 제안 : Assets/Scripts/Inventory/

  4. 사이클 매니저 (GameCycleManager 가칭)
     - VN → 피하기 → RPG(인벤토리) → VN 순서로 씬/상태를 전환하는 상위 컨트롤러
     - 각 파트의 결과값을 다음 파트로 전달하는 역할
     - 신규 폴더 제안 : Assets/Scripts/Core/GameFlow/ (또는 프로젝트 루트 Core)

================================================================
h. 기존 VN 엔진과의 연동 지점
================================================================

  - 씬 레벨 연결 방식 : 애디티브 씬 로딩 (확정, 26.09.14)
    · VN 씬(VisualNovel.unity)을 언로드하지 않은 채 미니게임 씬(예:
      Avoid.unity)을 SceneManager.LoadSceneAsync(씬명, LoadSceneMode.
      Additive)로 위에 얹는 방식
    · 채택 이유 : DialogueSystem/CharacterManager/HistoryManager/
      VariableStore 등 VN 핵심 싱글톤이 DontDestroyOnLoad 처리가 안
      되어 있어서(AudioManager만 예외) 단일 모드 LoadScene으로 씬을
      완전 교체하면 전부 파괴됨. 같은 씬 안에서 오브젝트 SetActive
      토글하는 대안도 있었으나 3~5단계 콘텐츠가 한 씬에 계속 쌓여
      비대해지는 문제가 있어 기각
    · 주의 : 애디티브 로딩 시 VN 배경/그래픽 패널이 미니게임 씬 뒤에
      그대로 남아있으므로, 미니게임 씬 카메라의 Depth를 VN 카메라보다
      높게, Clear Flags를 Solid Color(또는 Depth Only)로 설정해 가려야
      함 (에디터 작업)
    · 상세 설계 : Assets/Docs/2. ChangePlan/[26.09.14_20.24] 피하기
      게임 기초 구조 및 VN 연결.txt 참고 (Avoid 미니게임 기준으로
      작성됐지만 연결 방식 자체는 다른 미니게임에도 동일 적용)
  - VariableStore : 피하기/카드 장착 결과값을 변수로 저장 → VN의
    LL_Condition이 이 변수를 읽어 대사 분기에 반영
    (예: "피하기 실패 시 다른 대사")
  - CommandManager : 대사 중 [startAvoid(스테이지명)] 같은 커맨드로
    미니게임 씬/모드 진입 (애디티브 로딩 사용)
  - VNGameSave : 사이클 진행도(몇 번째 사이클, 보유 카드, 장착 구성 등)도
    함께 저장해야 함 → 기존 세이브 데이터 구조 확장 필요
  - 자동저장 체크포인트 (신규 필요, 확정 26.09.13) : 피하기 중 목숨을
    모두 소진해 타이틀로 돌아갈 경우, 마지막 자동저장 지점부터 재개해야
    하므로 사이클 시작 시점 등에 자동저장이 걸리는 지점을 VNGameSave에
    추가로 정의해야 함

  ══════════════════════════════════════

j. 각 단계에서 무엇이 생성/변경되는지
================================================================

  1단계 : 확정된 범위(대화/캐릭터/시나리오/선택지)가 기존 엔진으로
          이미 충족되어 신규 변경 없음 (26.09.14)
  2단계 : Assets/Scripts/Avoid/ (신규), VN↔피하기 전환 커맨드 추가
  3단계 : Assets/Scripts/Skills/ (또는 Cards/, 신규)
  4단계 : Assets/Scripts/Inventory/ (신규)
  5단계 : Assets/Scripts/Avoid/ 하위에 보스 관련 스크립트 추가
  각 단계 상세 변경 위치는 착수 시점에 [2. ChangePlan] 문서에서 확정

k. 주의할 점 / 미정 사항
================================================================

  ■ "피하기" 세부 규칙은 대부분 확정 (26.09.12 ~ 26.09.13)
    승리조건(보스 HP 0), 시간제한(보스별 상이), 목숨(3개)/부활(HP유지)/
    게임오버(타이틀 복귀) 처리, 조작(키보드+마우스), 전투 규모 확대
    방식까지 확정됨. 다만 아래는 여전히 미정 :
    - 보스 패턴 개수/종류, 페이즈 전환 디테일
    - 히트박스/판정 방식 세부
    - 화면 구성(밈피하기처럼 좁은 박스 vs 넓은 화면)
    - 스킬(카드) 쿨타임/발동 구조 세부
    → 확정되는 대로 별도 [2. ChangePlan] 문서로 세부 설계 진행

  ■ "RPG(덱빌딩)"의 정체는 재정의됐으나 세부 규칙은 여전히 미정
    턴제 전투가 아니라 스킬(카드) 수집/강화/장착 메타 시스템으로
    확정(26.09.13)됐으나, 카드 종류/획득 방식/강화 규칙/장착
    슬롯 수 등은 확정 필요
    → 확정되는 대로 별도 [2. ChangePlan] 문서로 세부 설계 진행

  ■ "1단계 VN 완성"의 범위 확정 (26.09.14)
    대화 시스템 + 캐릭터 + 시나리오 읽기(재생) + 선택지로 확정. 메인메뉴/
    세이브로드 UI/설정/갤러리/실제 스토리 콘텐츠(콘텐츠 파이프라인)는
    1단계 범위에서 제외됨 — 다만 어느 단계에 배정할지는 아직 미정
    (5단계 어디에도 명시적으로 들어있지 않음, 추후 확인 필요)

  ■ 세이브 시스템(ES3) 실사용 테스트 시점 확정 (26.09.14)
    26.09.13에 코드만 연결하고 미뤄뒀던 ES3 왕복(저장→로드) 실테스트는
    지금 바로 하지 않고, 4단계(인벤토리) 완성 후 사이클 진행도/보유
    카드/장착 구성 등 실제 저장 데이터가 늘어난 시점에 맞춰 확장하며
    진행하기로 함 (h절의 "세이브 데이터 구조 확장 필요"와 같은 시점)

  ■ 사이클 반복 횟수, 보스전 조건 등 콘텐츠 분량 관련 사항도 미정
    → 실제 스토리 챕터 작성 시 함께 확정

  ■ 선택지 결과가 변수에 자동으로 남지 않음 (VN 엔진, 확인 26.09.13)
    LL_Choice는 선택한 결과 대사만 재생할 뿐, "어떤 선택지를 골랐는지"
    자체를 변수로 자동 기록하지 않음. 나중에 그 선택을 조건문에서
    쓰려면 작가가 매번 선택지 결과 줄 안에 변수 대입 커맨드를 직접
    적어야 함. 지금은 챕터 수가 적어 괜찮지만, 콘텐츠 분량이 늘면
    반복 작업 부담이 커질 수 있어 자동화(예: choice 자체가 인덱스를
    변수로 남기는 기능)를 나중에 검토할 것

  ■ 실제 스토리 세부 내용은 여전히 미정
