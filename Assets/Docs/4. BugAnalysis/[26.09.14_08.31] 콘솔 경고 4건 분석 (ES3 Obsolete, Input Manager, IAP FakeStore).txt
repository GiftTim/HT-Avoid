b. 문제점
================================================================

  사용자가 제시한 콘솔 로그는 하나의 에러가 아니라, 서로 무관한
  4가지 경고/정보성 메시지가 한 번에 출력된 것임. 그중 컴파일 에러나
  런타임 크래시는 하나도 없고, 전부 "경고(warning)" 또는 "정보(info)"
  등급이다.

  [메시지 ①, ②] CS0618 : Light.cookieSize obsolete
    Assets/Plugins/Easy Save 3/Scripts/Types/Unity Types/ES3Type_Light.cs
    (36,48) 및 (99,7)
    → "Light.cookieSize has been deprecated. Use Light.cookieSize2D instead."

  [메시지 ③] CS0618 : EditorUtility.InstanceIDToObject(int) obsolete
    Assets/Plugins/Easy Save 3/Editor/ES3Postprocessor.cs (167,31)
    → "InstanceIDToObject(int) is obsolete. Use EditorUtility.EntityIdToObject instead."

  [메시지 ④] Input Manager 사용 경고
    "This project uses Input Manager, which is marked for deprecation.
     To manage input in your project, use the Input System package instead."

  [메시지 ⑤] IAP FakeStore 안내
    "The Microsoft GDK package is not installed. The selected store is FakeStore."

  [메시지 ⑥] UnityEditor.EditorApplication:Internal_CallUpdateFunctions ()
    → 이는 별도 문제가 아니라 ⑤ 로그가 에디터의 Update 루프에서
      출력됐다는 걸 알려주는 스택트레이스 꼬리표(로그 출력 위치)일 뿐,
      그 자체는 증상이 아님.

  네 가지 모두 원인과 성격이 전혀 다르므로, 아래 c~h 항목에서
  항목별로 나누어 분석한다.

c. 현재 상황 및 코드
================================================================

  ─────────────────────────────────────────────
  ① ② [ES3Type_Light.cs] cookieSize 경고 - 원인
  ─────────────────────────────────────────────
  Easy Save 3(서드파티 유료 에셋) 내부 코드에 이미 신/구 API 분기가
  들어가 있음 (프로젝트 코드가 아니라 벤더 코드):

      #if UNITY_6000_4_OR_NEWER
                writer.WriteProperty("cookieSize2D", instance.cookieSize2D);
      #else
                writer.WriteProperty("cookieSize", instance.cookieSize, ES3Type_float.Instance);
      #endif

  즉 Easy Save 3 제작사가 "Unity 6000.4 이상이면 새 API(cookieSize2D),
  아니면 구 API(cookieSize)" 로 이미 분기를 짜 놓았음.

  현재 프로젝트의 Unity 버전 확인 결과 (ProjectSettings/ProjectVersion.txt):
      m_EditorVersion: 6000.3.8f1

  → 6000.4 미만이므로 #else 분기, 즉 obsolete API인 cookieSize가
    컴파일되어 경고가 발생하는 것. 코드 자체는 정상 동작하며,
    "그 시점 Unity 버전에서 사용 가능한 API를 쓰고 있다"는 안내성 경고임.

  ─────────────────────────────────────────────
  ③ [ES3Postprocessor.cs] InstanceIDToObject 경고 - 원인
  ─────────────────────────────────────────────
  동일한 패턴의 벤더 코드:

      #if UNITY_6000_4_OR_NEWER
                      var obj = EditorUtility.EntityIdToObject(id);
      #else
                      var obj = EditorUtility.InstanceIDToObject(id);
      #endif

  → ①②와 완전히 같은 원인(Unity 6000.3.8f1 < 6000.4). Easy Save 3가
    이미 대응 코드를 준비해뒀고, Unity 버전이 6000.4 이상으로 올라가면
    자동으로 해소되는 경고.

  ─────────────────────────────────────────────
  ④ Input Manager 경고 - 원인
  ─────────────────────────────────────────────
  ProjectSettings/ProjectSettings.asset 확인 결과:
      activeInputHandler: 2   (0=Input Manager(Old), 1=Input System(New), 2=Both)

  → "Both"로 설정되어 있어 구 Input Manager가 여전히 활성화된 상태.
    Packages/manifest.json에는 com.unity.inputsystem: 1.18.0 이 이미
    설치되어 있으나, 프로젝트 코드가 아직 신 Input System으로
    전환되지 않아 "Both"를 유지 중.

  실제로 프로젝트 스크립트에서 구 Input 클래스를 사용 중인 곳 확인:
      Assets/Scripts/VisualNovel/Test/Testing_Architect.cs
      Assets/Scripts/VisualNovel/Test/Testing.cs
      Assets/Scripts/VisualNovel/Test/TestVariableStore.cs
      Assets/Scripts/VisualNovel/Test/TestHistory.cs
      Assets/Scripts/VisualNovel/Test/TestGameSave.cs
      Assets/Scripts/VisualNovel/Test/TestConversationQueue.cs
      Assets/Scripts/VisualNovel/Test/TestCommand.cs
      Assets/Scripts/VisualNovel/Test/TestCharacters.cs
    (전부 UnityEngine.Input.Get*() 계열 사용 - VN 엔진 테스트용 스크립트들)

  → "Both"를 "Input System Package (New)"로 바꾸면 위 8개 테스트
    스크립트의 UnityEngine.Input 호출이 즉시 동작하지 않게 됨.
    즉 이 경고는 "아직 신 Input System으로 마이그레이션을 완료하지
    않은 상태"를 정확히 반영하는 의도된 경고이지, 설정 실수가 아님.

  ─────────────────────────────────────────────
  ⑤ IAP FakeStore 안내 - 원인
  ─────────────────────────────────────────────
  Packages/manifest.json 확인 결과 com.unity.purchasing: 5.4.3 (Unity IAP)
  이 설치되어 있음. Unity IAP는 에디터에서 플레이할 때 실제 스토어
  (Google Play, App Store, Microsoft GDK/Xbox 등) SDK가 연결되어
  있지 않으면 테스트용 더미 스토어인 "FakeStore"로 자동 대체하고,
  그 사실을 콘솔에 안내로 출력함.

  → 이 프로젝트는 IAP를 Xbox/GDK 플랫폼용으로 설정한 적이 없고
    (Packages/manifest.json, ProjectSettings 어디에도 GDK 관련 설정 없음),
    에디터에서 그냥 플레이 중이므로 FakeStore가 뜨는 것이 정상 동작.
    에러가 아니라 "지금은 테스트 스토어를 쓰고 있다"는 안내 로그.


================================================================
d. 해결 방식
================================================================

  ① ② ③ (Easy Save 3 CS0618 경고 3건)
    → 코드를 수정하지 않고 그대로 둔다.
      (Easy Save 3 자체 업데이트로 obsolete 아님이 확정되거나,
       프로젝트 Unity 버전을 6000.4 이상으로 올리면 #if 분기에 의해
       자동으로 사라지는 경고이기 때문)

  ④ (Input Manager 경고)
    → 지금 당장 activeInputHandler를 바꾸지 않는다.
      다만 "1. Plan/전체 개발 로드맵"의 Phase 1(엔진 점검) 단계에서
      VN 엔진 및 Test 스크립트들의 Input 사용처를 신 Input System
      (UnityEngine.InputSystem)으로 전환하는 작업을 별도 항목으로
      등록해 추후 진행한다.

  ⑤ (IAP FakeStore 안내)
    → 아무 조치도 필요 없음. 실제 배포 플랫폼(스토어)이 정해지고
      해당 스토어용 IAP 설정을 프로젝트에 반영하는 시점에 자연히
      사라지는 로그.


================================================================
e. 해당 방식을 선택한 이유
================================================================

  [① ② ③ 관련 대안 비교]

  [대안 1] Easy Save 3 벤더 코드(ES3Type_Light.cs, ES3Postprocessor.cs)를
           직접 열어 #else 분기를 지우고 cookieSize2D / EntityIdToObject만
           남기기
    - 단점 : Unity 6000.3.8f1에는 cookieSize2D, EntityIdToObject API가
             아직 존재하지 않을 수 있어 오히려 컴파일 에러로 악화될 위험.
             또한 Asset Store에서 Easy Save 3를 업데이트하면 이 수정이
             통째로 덮어써져 사라짐 (벤더 코드를 직접 고치는 것 자체가
             유지보수 관점에서 나쁨).

  [대안 2] csc.rsp(Assets/csc.rsp)에 -nowarn:0618 추가해 프로젝트
           전역에서 CS0618 경고 자체를 침묵시키기
    - 단점 : Easy Save 3는 별도 asmdef 없이 기본 Assembly-CSharp /
             Assembly-CSharp-Editor에 함께 컴파일되므로, 이렇게 하면
             프로젝트 자체 코드에서 앞으로 발생할 수 있는 진짜
             obsolete API 경고까지 전부 숨겨버림. 경고 3개를 지우려다
             더 중요한 신호를 잃는 셈이라 부적절.

  [대안 3] Easy Save 3만 별도 asmdef로 분리한 뒤 그 asmdef에만
           경고 억제 설정 적용
    - 단점 : 단순 경고 3건을 지우자고 벤더 폴더 구조를 asmdef로
             바꾸는 것은 리플렉션 기반 동작(Easy Save 3는 사용자
             타입을 리플렉션으로 스캔)에 영향이 없는지 검증이 추가로
             필요한 구조 변경이라 과잉 대응.

  [선택 이유 - d 방식 : 그대로 둔다]
    - 세 경고 모두 "지금 당장 아무 것도 망가지지 않는" 순수 경고이고,
      원인(Unity 버전 < 6000.4)도 명확하며, 해소 조건(버전 업/에셋 업데이트)도
      이미 벤더 코드에 준비되어 있음.
    - 굳이 벤더 코드/전역 설정을 건드려서 얻는 실익이 없고, 오히려
      위 대안들처럼 부작용(컴파일 에러화, 경고 은폐, 구조 변경 리스크)이
      더 큼.

  [④ 관련 대안 비교]

  [대안 1] 지금 바로 activeInputHandler를 1(Input System 전용)로 변경
    - 단점 : Test 폴더의 8개 스크립트가 UnityEngine.Input을 그대로
             호출하고 있어 즉시 컴파일 에러 또는 입력 미동작 발생.
             "경고 하나 지우려다 테스트 코드 전부를 깨뜨리는" 손해가 큼.

  [선택 이유 - d 방식 : 지금은 유지, Phase 1에 마이그레이션 항목으로 등록]
    - 이 경고는 실제로 "구 Input Manager에 의존하는 코드가 아직 남아있다"는
      사실을 정확히 알려주는 것이므로, 당장 지우는 게 아니라 근본
      원인(Input 사용처 마이그레이션)을 계획에 반영하는 것이 맞는 순서.
    - 이미 1. Plan 문서의 로드맵에 Phase 1(엔진 점검) 단계가 존재하므로,
      그 작업 단위 안에 편입시키는 것이 문서 관리 원칙과도 맞음.

  [⑤ 관련 대안 비교]

  [대안 1] com.unity.purchasing 패키지를 제거해서 로그 자체를 없애기
    - 단점 : 추후 인앱결제 기능이 필요해질 경우 다시 설치/설정해야 함.
             현재 이 메시지로 인해 발생하는 실질적 문제(에러, 기능 이상)가
             전혀 없으므로 패키지를 지울 이유가 없음.

  [선택 이유 - d 방식 : 조치 없음]
    - 에디터에서 플레이할 때 실제 스토어가 없으니 테스트용 FakeStore를
      쓴다는, 정상적이고 의도된 동작에 대한 안내이기 때문.

h. 주의할 점
================================================================

  ■ 이 4가지는 서로 다른 문제이며, "한 번에 다 고쳐야 하는 하나의 버그"가
    아님. 콘솔에 같이 찍혔다고 해서 같은 원인으로 묶어서 접근하면 안 됨.

  ■ ①②③ (Easy Save 3 경고)
    - Assets/Plugins/Easy Save 3 안의 파일은 벤더(서드파티) 코드이므로
      직접 수정하지 말 것. 에셋스토어에서 업데이트를 받으면 수정 내용이
      통째로 사라짐.
    - Unity 버전을 6000.4 이상으로 올리는 순간 이 경고들은 코드 변경 없이
      자동으로 사라지므로, 그 전까지는 "정상적으로 발생 중인 경고"로
      취급하고 무시해도 됨.

  ■ ④ (Input Manager 경고)
    - activeInputHandler를 섣불리 "Input System (New)" 전용으로 바꾸지
      말 것. Test 폴더의 8개 스크립트(Testing.cs, TestCommand.cs 등)가
      UnityEngine.Input에 의존하고 있어 즉시 깨짐.
    - 마이그레이션을 진행하게 되면 VN 엔진 본체(Assets/Scripts/VisualNovel/Core)
      쪽에도 구 Input 사용처가 있는지 별도로 전수 조사가 필요함 (이번
      분석은 Test 폴더까지만 확인함).

  ■ ⑤ (IAP FakeStore 안내)
    - 실제 배포 플랫폼(스토어)이 정해지지 않은 현재 개발 단계에서는
      정상 동작이지만, 추후 특정 스토어(Steam/Google Play 등)로 배포를
      확정하면 그때 IAP 스토어 설정을 그 플랫폼에 맞게 다시 잡아야
      FakeStore 안내가 실제 스토어 연동으로 바뀜.

  ■ 이 문서는 "지금 고칠 필요 없음"이 결론이므로, 추후 실제로 위 항목
    중 하나를 손대게 되면(Unity 버전 업, Input System 마이그레이션 등)
    이 문서를 참고 자료로만 남기고, 실제 변경 작업은 2. ChangePlan에
    새 계획 문서를 만들어 진행할 것 (Assets/Docs 문서 관리 규칙 참고).
